Multi-Certificate Support Inside One PDF - Implementation Plan

This document explains how multi-certificate support was implemented so one uploaded PDF can contain multiple BIR 2307 certificates and the system can process them page by page.

1. Goal

Support this workflow:

- user uploads one PDF
- the PDF may contain multiple BIR 2307 certificate pages
- non-certificate pages are ignored
- each detected certificate page is processed as its own certificate result

2. Status Snapshot

[completed] Add page-aware workflow state instead of assuming one document per upload.
[completed] Split the uploaded PDF into one-page PDFs before OCR.
[completed] Classify each page as certificate or non-certificate.
[completed] Keep upload-level batch summary data for detected, ignored, valid, failed, and duplicate pages.
[completed] Detect duplicate certificate pages inside the same PDF before normalization.
[completed] Normalize, masterlist-check, and validate certificate pages individually.
[completed] Persist one successful result row per certificate page.
[completed] Add schema support so one upload can own many certificate result rows.
[completed] Update upload and document UI summaries to show certificate counts from one PDF.

4. High-Level Flow

Upload queued
  -> load_input
  -> extract_document
     -> split PDF into pages
     -> OCR each page
     -> classify each page
  -> check_duplicate_page
     -> if same certificate page appears twice in the same PDF: persist_duplicate
  -> normalize_fields
  -> check_masterlist
  -> validate_rules
  -> dedupe_check
     -> if already processed before: persist_duplicate
     -> if not duplicate: persist_validated
  -> reconcile_document
  -> finalize_workflow

5. Implementation Details

Step 1. Make the workflow page-aware

Files:
- backend/worker/src/langgraph/types.ts
- backend/worker/src/langgraph/graph.ts

What changed:

- Added `pages` to workflow state.
- Added `WorkflowPageState` so each PDF page can carry:
  - `pageNumber`
  - `classification`
  - `extraction`
  - `normalized`
  - `validation`
  - `masterlistLookup`
  - per-page decision data
- Added `batchSummary` to track upload-level counts:
  - total pages
  - detected certificate pages
  - ignored pages
  - valid pages
  - failed pages
  - duplicate pages

Why this mattered:

Before this, the workflow behaved like one upload always meant one extracted certificate. Multi-certificate support required the graph state to carry both:

- upload-level state
- page-level certificate state

Step 2. Split one PDF into one-page PDFs

File:
- backend/worker/src/langgraph/utils/pageProcessing.ts

What changed:

- Added `splitPdfPages(source)` using `pdf-lib`.
- Each source PDF page is copied into a new single-page PDF buffer.
- Pages keep stable 1-based numbering.

Why this mattered:

The OCR pipeline can now operate page by page, and later steps can persist page-specific results and page numbers.

Step 3. OCR and classify every page

Files:
- backend/worker/src/langgraph/nodes/extractDocument.ts
- backend/worker/src/langgraph/utils/pageProcessing.ts

What changed:

- `extractDocument` no longer extracts only one document blob.
- It loops over the split pages and runs OCR for each page.
- Each page is classified with `classifyPageText(...)` as:
  - `certificate`
  - `non_certificate`
- The node builds `batchSummary.certificatePageNumbers` and `batchSummary.ignoredPageNumbers`.

Classification rules look for OCR evidence such as:

- `BIR Form No. 2307`
- `Certificate of Creditable Tax Withheld at Source`
- official BIR header text
- noisy but recognizable OCR combinations of those markers

Behavior:

- If zero certificate pages are detected, the upload becomes an error.
- If certificate pages exist, non-certificate pages stay in `pages` but are ignored by the certificate-processing path.

Step 4. Keep backward compatibility with a primary page

File:
- backend/worker/src/langgraph/nodes/extractDocument.ts

What changed:

- After page extraction, the node still assigns top-level `state.extraction` and `state.extracted` from the first detected certificate page.

Why this mattered:

This let the workflow become multi-certificate aware without forcing every downstream caller to switch away from top-level fields immediately. The real source of truth is now `state.pages`, but the first certificate page is still exposed at the top level for compatibility.

Step 5. Detect duplicate certificate pages inside the same PDF

Files:
- backend/worker/src/langgraph/nodes/checkDuplicatePage.ts
- backend/worker/src/langgraph/utils/pageProcessing.ts

What changed:

- Added `findDuplicateCertificatePages(...)`.
- Only pages classified as `certificate` are checked.
- OCR text is normalized and hashed.
- If two certificate pages in the same upload have the same normalized text fingerprint, the later page is marked as a duplicate of the earlier page.

Behavior:

- duplicate page numbers are written into `batchSummary.duplicatePageNumbers`
- the upload is routed to `persist_duplicate`
- this happens before normalization and before historical dedupe

Step 6. Normalize each detected certificate page independently

File:
- backend/worker/src/langgraph/nodes/normalizeFields.ts

What changed:

- `normalizeFields` now loops through `certificate` pages instead of normalizing one upload-level payload.
- Each certificate page gets its own `page.normalized`.
- The page list is rebuilt with normalized data attached to the correct page number.

Why this mattered:

Each certificate page inside the same PDF can now produce its own structured data instead of competing for one shared normalized result.

Step 7. Run masterlist and validation checks per page

Files:
- backend/worker/src/langgraph/nodes/checkMasterlist.ts
- backend/worker/src/langgraph/nodes/validateRules.ts

What changed:

- Masterlist lookup now runs for each certificate page.
- Validation rules now run for each certificate page.
- Failed page numbers are tracked in `batchSummary.failedPageNumbers`.
- Valid page numbers are tracked in `batchSummary.validPageNumbers`.

Current behavior:

- if any certificate page fails masterlist lookup or validation, the upload is treated as an error batch
- the system does not partially persist only the valid pages from that upload

That behavior is important: the workflow is page-aware, but persistence is still all-or-nothing for validation success versus batch failure.

Step 8. Add historical dedupe that understands multi-page uploads

Files:
- backend/worker/src/langgraph/nodes/dedupeCheck.ts
- backend/worker/src/langgraph/utils/dedupe.ts

What changed:

- Added page-level and batch-level dedupe fingerprints.
- The worker now checks duplicates using:
  - same source file revision
  - same original filename
  - same source hash
  - same normalized certificate data

For multi-certificate uploads:

- each certificate page gets its own normalized data fingerprint
- the upload also gets a batch fingerprint built from the set of page fingerprints
- duplicate matches can point back to a stored certificate row or to a previously stored upload-level duplicate/error artifact

Why this mattered:

Without page-level fingerprints, two different multi-page PDFs containing the same certificate set would not match reliably.

Step 9. Persist one certificate result row per page

File:
- backend/worker/src/langgraph/nodes/persistResults.ts

What changed:

- `persistResults` filters to certificate pages only.
- It loops through those pages and persists each one separately.
- Each persisted page gets:
  - its own raw extraction JSON
  - its own final result JSON
  - its own renamed PDF containing only that page
  - its own `document_results` row

Important stored fields:

- `documentKind = certificate`
- `pageNumber = original page number from the uploaded PDF`
- `artifactKey` and `finalKey` for that page's artifacts
- per-page dedupe fingerprint

Why this mattered:

This is the core change that turned one upload into many certificate outputs.

Step 10. Keep upload-level rows for duplicate and error outcomes

Files:
- backend/worker/src/langgraph/nodes/persistDuplicate.ts
- backend/worker/src/langgraph/nodes/persistValidationFail.ts

What changed:

- Duplicate and error outcomes are still stored as upload-level rows.
- Those rows use:
  - `documentKind = upload`
  - `pageNumber = null`
- Their payload still contains all page data and batch summary data.

Why this mattered:

The system needs both models:

- page-level certificate rows for successful processing
- upload-level rows for duplicate and error batches

This also gives future dedupe checks a stable place to inspect old failed or duplicate uploads.

Step 11. Change the schema so one upload can own many certificate results

Files:
- backend/worker/src/db/migrations/0005_multi_certificate_results.sql
- backend/worker/src/db/schema.ts
- webapp/tax-track/src/lib/migrations/0007_multi_certificate_results.sql
- webapp/tax-track/src/lib/schema.ts

What changed:

- Added `document_kind` to `document_results`
- Added `page_number` to `document_results`
- Added a unique guard on:
  - `upload_id`
  - `document_kind`
  - `COALESCE(page_number, -1)`

Effect:

- one upload can have many `certificate` rows as long as page numbers differ
- the same upload can still have only one upload-level row for duplicate/error handling

Step 12. Update frontend summaries for one PDF with many certificates

Files:
- webapp/tax-track/src/lib/intake-server.ts
- webapp/tax-track/src/lib/upload-intake-view-model.ts
- webapp/tax-track/src/components/upload-intake-page.tsx

What changed:

- Upload summary parsing now reads `batchSummary` from result payloads.
- The UI can show values such as:
  - detected certificates
  - validated certificates
  - skipped pages
  - needs review
- Jobs table labels now reflect certificate counts from one upload, for example:
  - `3 detected / 3 valid`
  - `2 detected / processing`
  - `4 detected / 1 needs review`

User-facing effect:

The upload page now describes the system correctly:

- one PDF per upload
- multiple certificates can exist inside that PDF
- non-certificate pages are ignored

6. Current Design Summary

The implementation changed the system from:

- one upload -> one certificate result

to:

- one upload -> many page states during processing
- one upload -> many certificate result rows on success
- one upload -> one upload-level row on duplicate or error

7. Important Current Behavior

- Only pages classified as certificate move through normalization, masterlist checking, validation, and success persistence.
- Non-certificate pages are ignored, but they still count in `totalPages` and `ignoredPageNumbers`.
- If no certificate pages are found, the upload fails.
- If duplicate certificate pages are found inside the same PDF, the whole upload is marked duplicate.
- If any certificate page fails masterlist or validation, the whole upload is marked error.
- Successful uploads persist certificate rows only; they do not also create a second upload-level success row.
